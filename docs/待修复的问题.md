## Harness

## SKILL
对现有 16 个 WebCompass Edit Skill 统一优化，目标是：**让模型在 Edit 时尽可能直接找到并复用现成代码，并覆盖 WebCompass 对应题型的常见功能要求。**

每个 Skill 应包含：

1. **Benchmark 对齐**

   * 根据 WebCompass 该类别真实 Edit 指令和评测重点设计。
   * 覆盖该类别常见子功能和功能组合，不按泛化前端教程设计。

2. **完整 Reference Code**

   * `references/` 提供可直接运行、可直接复制复用的实现。
   * 不只提供最小 demo，要覆盖该类别高频能力。
   * 常用逻辑尽量拆成独立函数/模块，方便局部复制。

3. **明确复用入口**

   * 写清主 API、核心参数、输入输出、生命周期。
   * 明确已有网页的哪些数据、DOM、状态应该接入哪里。

4. **宿主状态优先**

   * Reference 组件不能偷偷维护独立业务数据源。
   * 编辑、删除、批量操作等必须展示如何写回已有网页状态。
   * 组件内部只维护必要 UI 状态。

5. **最小正确接入示例**

   * 示例不能只是“能跑”，必须展示关键数据流和回调。
   * 文档里强调的重要规则，示例代码必须实际体现。
   * 避免模型因为照抄过度简化示例而产生错误实现。

6. **覆盖常见组合**

   * 除基础示例外，补少量 WebCompass 高频组合，例如：
     `filter + sort`、`edit + pagination`、`selection + bulk action`。
   * 不需要大量案例，只保留最有代表性的组合。

7. **特有风险**

   * 只写该 Skill 特有、容易导致 WebCompass Edit 失败的问题。
   * 例如状态不同步、排序使用展示值而非真实值、拖拽后数据未写回等。
   * 通用规则放到公共 Skill，不在 16 个 Skill 里重复。

8. **保持轻量**

   * Skill 文档本身保持短。
   * 信息量主要放在高质量 reference code，而不是长篇说明。
   * 优先“现成代码可复用”，而不是让模型重新理解并实现一遍。

最终每个 Skill 推荐结构：

```text
SKILL.md
├── 参考代码
├── 能力覆盖
├── 接入位置
├── API / 数据流
├── 特有风险
└── 最小正确示例

references/
├── 完整核心实现
├── 样式
└── 必要的组合/辅助实现
```

核心标准：**如果 WebCompass 出一道该类别的典型 Edit 题，模型应该主要通过改配置、接数据、接回调和少量适配完成，而不是重新实现整个功能。**
